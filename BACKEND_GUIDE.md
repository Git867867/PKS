# Сервер бронирования. Как он устроен и что показать на защите

Это контрольная №3. Консольное меню и окно JavaFX остаются как были. Рядом появился отдельный сервер: программа, которая принимает HTTP-запросы, читает и пишет PostgreSQL и отдает JSON. Будущее Android-приложение из КР №4 будет вызывать те же адреса.

Пример преподавателя назывался Student Hub. Имена оттуда не оставлены. Соответствие такое:

| В примере | У нас |
| --- | --- |
| Student | Бронирование, `Booking` |
| StudyGroup | Пассажир, `Passenger` |
| StudentStatus | `BookingStatus`: CREATED, CONFIRMED, COMPLETED, CANCELLED |
| RiskLevel | `PriorityLevel`: приоритет обслуживания LOW, MEDIUM, HIGH |
| StudentNote | `BookingNote` |
| student_tag | таблица `tags` и связь `booking_tags` |
| UserAccount, RefreshSession, AuditEvent | те же роли, но свои таблицы |

## Две базы, их нельзя перепутать

JavaFX и консоль ходят в базу `airline_booking` на порту **5432**. Это база КР №1.

Сервер КР №3 поднимает свою базу в Docker и публикует ее только на **127.0.0.1:56080**. В примере преподавателя порт 55432, но Windows на этом компьютере резервирует диапазон 55380–55479, поэтому в `.env` стоит 56080. Внутри Docker база по-прежнему слушает 5432. Пользователь базы `airline_app`. Пароль лежит в `.env`, не в Java-коде.

Первая миграция не содержит `DROP`. Если случайно направить Flyway на старую базу, создание уже существующих таблиц остановится и данные не сотрутся.

Запуск из корня проекта:

```powershell
.\backend\start-compose.ps1
```

Скрипт вызывает `docker compose` с файлом `.env`. PostgreSQL стартует первым. У него есть проверка `pg_isready`. Сервер стартует после нее. Его проверка дергает `http://localhost:8080/actuator/health`. Обычный `docker compose down` удаляет контейнеры, но не volume `airline_pg`, поэтому данные остаются.

На компьютере стоит JDK 17, его хватает для JavaFX. Сервер собирается внутри образа с JDK 21. Так требует задание, и локальный JDK 17 для этого не нужен.

## Слои

Пакеты те, которые просит задание:

| Пакет | Зачем |
| --- | --- |
| `controller` | Принимает HTTP и вызывает сервис. Сущности наружу не отдает. |
| `service` | Правила, транзакции, приоритет, пароли, CSV. |
| `repository` | Spring Data JPA. SQL строкой из пользовательского ввода не собирается. |
| `domain` | Таблицы и enum. |
| `dto` | JSON, который приходит и уходит. На полях стоят аннотации Bean Validation. |
| `security` | JWT, текущий пользователь, номер запроса. |
| `filter` | Белый список сортировки и фильтр бронирований через Criteria API. |
| `error` | Один JSON для всех ошибок. Стек клиенту не отдается. |
| `config` | Security, Swagger, настройки из `application.yml`. |
| `db/migration` | Flyway. |

Числовой `id` из КР №1 сохранен: так совпадает первая миграция. В API наружу уходит `public_id`, это UUID. Код бронирования `BK-000001` нужен для CSV: по нему запись обновляется.

Поле `version` увеличивается при каждом изменении. Если два человека сохраняют одну карточку, второй получает HTTP 409 и текст «Запись уже изменили».

Удаление с сайта — это не `DELETE` из таблицы, а `archived = true`. Восстановление ставит флаг обратно. Физически удалить может только администратор, и только из архива. Флаг `PERMANENT_DELETE_ENABLED` в `.env` это разрешает.

## Приоритет

Считается в `PriorityCalculator` при каждом сохранении и один раз проставлен миграцией для старых строк.

- Завершенное или отмененное бронирование — низкий приоритет.
- Иначе, если цена от 10000 или вылет уже прошел либо наступит в ближайшие 48 часов — высокий.
- Иначе, если цена от 7000 — средний.
- Иначе низкий.

Это и есть «вычисляемый показатель» из задания. Он хранится в колонке, поэтому по нему можно фильтровать. Логический признак — `refundable`, возвратный билет.

Новое бронирование всегда получает статус CREATED. Дальше разрешены только переходы из КР №1: CREATED в CONFIRMED или CANCELLED, CONFIRMED в COMPLETED или CANCELLED. Оставлять тот же статус можно.

Правила рейса, городов, цены и даты те же, что в JavaFX. Они собраны в `BookingRules`.

## Кто что может

Роли три: `VIEWER` смотрит, `EDITOR` еще меняет бронирования и заметки, `ADMIN` еще управляет пассажирами, пользователями, аудитом и окончательным удалением. Список ролей написан у каждого адреса явно, без скрытой иерархии. Администратор проходит туда, где указан `ADMIN`, и на запись бронирований, потому что у этих адресов указаны и `EDITOR`, и `ADMIN`.

Пароль хранится только как хеш BCrypt. В ответах пароля нет. После создания или сброса пароль временный: `mustChangePassword = true`. Пока флаг включен, фильтр пускает только смену пароля, профиль и выход. Остальное отвечает 403 с кодом `PASSWORD_CHANGE_REQUIRED`.

Пять неверных паролей блокируют вход на 15 минут. Неизвестный email и неверный пароль получают один и тот же текст, чтобы нельзя было узнать, есть ли такой пользователь. Отключенная учетная запись войти не может.

Короткий access JWT живет 15 минут и приходит в JSON. Его ставят в заголовок `Authorization: Bearer ...`. Refresh-токен — случайная строка. В базе лежит только ее SHA-256. Для страницы он еще записан в cookie `HttpOnly`, путь `/api/auth`. Для будущего Android тот же токен есть в JSON. При обновлении старая сессия гасится и выдается новая. Выход гасит сессию.

Первый администратор создается при старте, если такого email еще нет. Логин и временный пароль берутся из `.env`: `admin@airline.local` и `Adm1!Airline26`.

## Адреса

Слова `items` и `references` из задания заменены на предметные.

| Действие | Метод и путь |
| --- | --- |
| Вход, обновление, выход, профиль, смена пароля | `/api/auth/login`, `/refresh`, `/logout`, `/me`, `/password` |
| Список, карточка, создание, изменение | `GET/POST /api/bookings`, `GET/PUT /api/bookings/{id}` |
| Архив и восстановление | `DELETE /api/bookings/{id}`, `POST /api/bookings/{id}/restore` |
| Удаление администратором | `DELETE /api/bookings/{id}/permanent` |
| Массовые операции | `POST /api/bookings/bulk` |
| Проверка и применение CSV, экспорт | `POST /api/bookings/import/preview`, `.../apply`, `GET /api/bookings/export` |
| Заметки | `/api/bookings/{id}/notes` |
| Пассажиры | `GET/POST /api/passengers`, `PUT /api/passengers/{id}`, `POST /api/passengers/{id}/active` |
| Аналитика | `GET /api/analytics/summary` |
| Пользователи и аудит | `/api/admin/users`, `/api/admin/audit` |

Список бронирований принимает поиск `q`, пассажира, статус, возвратность, приоритет, тег, `view=active|archived|all`, цену с операцией `GT|GTE|LT|LTE|EQ`, сортировку `departureDate|price|status|createdAt` и страницу. Размер страницы не больше 100. Поле сортировки берется из белого списка. Значение фильтра уходит в запрос параметром, а не склейкой строки.

Ошибки всегда JSON: `status`, `error`, `message`, `path`, `correlationId`, `timestamp`. 400 — плохие данные, 401 — нет входа, 403 — мало прав, 404 — нет записи, 409 — конфликт версии или дубликат. Каждый запрос получает заголовок `X-Correlation-Id`, тот же номер пишется в аудит.

Swagger открыт по адресу `/swagger-ui.html` без JWT: браузер открывает страницу обычным переходом и не умеет сам подставить Bearer. Сами методы API без токена отвечают 401. В Swagger токен вставляется кнопкой Authorize. На защите это стоит сказать прямо.

Страница на `http://localhost:8080/` — обычные HTML, CSS и JS из `backend/src/main/resources/static`. React не использовался: задание разрешает другое решение, а эту страницу проще объяснить. Access-токен лежит в `sessionStorage`. Refresh уходит cookie, потому что запросы идут с `credentials: include`. Кнопки на странице прячутся по роли, но отказ все равно делает сервер.

## Что нажать на защите

1. `.\backend\start-compose.ps1` и открыть health.
2. Войти временным паролем и сразу сменить его.
3. Создать пользователя с ролью просмотра, войти им и показать, что изменение отвечает 403.
4. Создать и изменить бронирование. Показать, что приоритет пересчитался.
5. Поиск, фильтр по статусу и цене, сортировка, вторая страница.
6. Архив и восстановление. Массовая смена статуса или тега. Показать в ответе успешные id и ошибки.
7. Заметка, в том числе закрепленная.
8. Проверка `backend/sample-import.csv`, затем применение. Экспорт с тем же фильтром, что на экране.
9. Аналитика: всего, активные, архив, возвратные, средняя цена, три группировки.
10. Сброс пароля пользователя и журнал аудита. В строке аудита есть пользователь, тип, время, описание и correlation id.
11. Swagger.
12. В базе: таблицы Flyway `flyway_schema_history`, внешние ключи, индексы по коду, статусу, приоритету и архиву.

Тесты лежат в `backend/src/test`. Контекст Spring поднимается на H2, без Flyway. Отдельно проверяются приоритет, политика пароля и запрет сортировки по произвольному полю.
