## 1. Общее описание системы

Приложение для бронирования авиабилетов. Данные хранятся в PostgreSQL, доступ через JDBC.

КР №1 — консольное меню. КР №2 добавляет настольное окно JavaFX и не заменяет предметную область: те же таблицы `passengers` и `bookings`, те же сервисы и те же SQL-запросы. Разбор окна, причин выбранных решений и ответов на защите — в [разделе 17](#17-кр-2-настольное-javafx-приложение).

Основные функции:
- CRUD для бронирований и пассажиров
- Поиск по номеру рейса и имени/фамилии пассажира
- Фильтрация по статусу, городу, диапазону дат
- Сортировка по дате, цене, статусу (Stream API)
- Статистика (6 показателей)
- Экспорт в Excel (.xlsx) и CSV
- 3 роли: Администратор, Менеджер, Клиент
- Валидация всех полей при вводе

## 2. Выбор технологий

### Java 17 и JavaFX 21

Объектно-ориентированный язык со строгой типизацией. Проект КР №1 собран на Java 17. В методичке КР №2 указана Java 21, потому что так собран чужой пример из архива. На рабочем компьютере установлен JDK 17, а JavaFX 21 официально запускается на Java 17 и новее. Код окна не использует возможности, которые появились только в Java 21, поэтому в `pom.xml` оставлен `<maven.compiler.release>17</maven.compiler.release>`. Если на защите потребуется именно JDK 21, достаточно поставить его и заменить это число на 21.

JavaFX — библиотека окон: кнопки, таблицы, формы, диалоги. Версия 21.0.8, как в примере методички.

### Apache Maven

Система сборки с автоматическим управлением зависимостями. В проекте 3 внешние библиотеки -- без Maven пришлось бы вручную скачивать десятки JAR-файлов.

### PostgreSQL

Бесплатная реляционная СУБД. Поддерживает CHECK-ограничения, FOREIGN KEY, BIGSERIAL. Выбрана за строгость и широкое применение.

### JDBC

Стандартный Java API для работы с БД. Дает полный контроль над SQL-запросами. PreparedStatement защищает от SQL-инъекций. try-with-resources гарантирует закрытие ресурсов.

### Apache POI

Библиотека для работы с Excel (.xlsx). Позволяет стилизовать ячейки, задавать ширину колонок.

## 3. Архитектура приложения

Многослойная архитектура:

```
Окно JavaFX (FXML + Controller) -- кнопки, таблица, диалоги
Консоль КР №1 (ConsoleMenu)     -- старый текстовый вход, те же сервисы
Service (BookingService, ...)   -- бизнес-логика, валидация, отбор для таблицы
Repository (BookingRepository)  -- SQL-запросы через JDBC
PostgreSQL (airline_booking)    -- хранение данных
```

Зависимости идут строго сверху вниз. Ни один нижний слой не знает о верхнем.

Объекты создаются в Main.java и передаются через конструкторы:

```java
PassengerRepository passengerRepository = new PassengerRepository();
BookingRepository bookingRepository = new BookingRepository();
PassengerService passengerService = new PassengerService(passengerRepository);
BookingService bookingService = new BookingService(bookingRepository, passengerRepository);
ConsoleMenu menu = new ConsoleMenu(bookingService, passengerService);
menu.run();
```

## 5. Слой модели

### Passenger.java

Поля (все private): id, firstName, lastName, email, phone, passportNumber.
Два конструктора: без id (для создания) и с id (для маппинга из ResultSet).
Тип String для телефона и паспорта, потому что они содержат символы (+, -, пробел).

### Booking.java

Поля: id, passengerId, flightNumber, departureCity, arrivalCity, departureDate (LocalDateTime), price (BigDecimal), status (BookingStatus), createdAt, passengerFullName.

BigDecimal для цены вместо double -- double дает ошибки округления (0.1 + 0.2 = 0.30000000000000004).
LocalDateTime вместо java.util.Date -- современный, иммутабельный API.

### BookingStatus.java

Enum с 4 значениями: CREATED, CONFIRMED, COMPLETED, CANCELLED.
Содержит карту допустимых переходов:
- CREATED -> CONFIRMED, CANCELLED
- CONFIRMED -> COMPLETED, CANCELLED
- COMPLETED -> (терминальный)
- CANCELLED -> (терминальный)

Метод canTransitionTo() проверяет допустимость перехода.
Метод fromString() парсит строку в enum с понятным сообщением об ошибке.

### UserRole.java

Enum с 3 значениями: ADMIN, MANAGER, CLIENT.
Каждая роль имеет displayName на русском.
Определяет доступные пункты меню для пользователя.

## 6. Слой репозитория

### CrudRepository<T> -- интерфейс

5 методов: save, findAll, findById, update, deleteById.
Generic <T> позволяет не дублировать интерфейс для каждой сущности.
Optional<T> в findById явно показывает, что результат может отсутствовать.

### PassengerRepository

Реализует CrudRepository<Passenger>. Дополнительные методы:
- existsById, existsByEmail, existsByPassportNumber -- для валидации
- existsByEmailExcludingId, existsByPassportNumberExcludingId -- для валидации при обновлении

Все запросы через PreparedStatement (защита от SQL-инъекций) и try-with-resources (автозакрытие ресурсов).

### BookingRepository

Реализует CrudRepository<Booking>. Дополнительные методы:
- findByPassengerId -- для роли CLIENT (показать только свои бронирования)
- searchByFlightNumber -- поиск по части номера рейса (ILIKE)
- searchByPassengerName -- поиск по имени ИЛИ фамилии (OR-условие)
- filterByStatus, filterByCity, filterByDateRange
- countAll, countByStatus, averagePrice, mostPopularRoute, topPassenger, totalRevenue

Все SELECT-запросы используют JOIN с таблицей passengers для вывода имени пассажира.

## 7. Слой сервисов

### PassengerService

Валидация при создании и обновлении пассажира:
- Имя/фамилия: только буквы и дефис (regex `[а-яА-ЯёЁa-zA-Z\-]+`)
- Email: формат xxx@xxx.xx (regex)
- Телефон: формат +7-XXX-XXX-XXXX (regex `\+7-\d{3}-\d{3}-\d{4}`)
- Паспорт: формат XXXX XXXXXX (regex `\d{4} \d{6}`)
- Уникальность email и паспорта (с учетом обновления)

### BookingService

Валидация при создании и обновлении бронирования:
- Номер рейса: формат XX-1234 (regex `[A-Za-z]{1,3}-\d{1,4}`)
- Города: только буквы, пробелы, дефисы (regex)
- Города вылета и прилета не совпадают
- Дата не в прошлом и не более чем через 6 месяцев. Если при редактировании дату не меняли, старая дата сохраняется: иначе тестовые рейсы, которые уже вылетели, нельзя было бы поправить.
- Длина городов не больше 100 символов, номер рейса не больше 10.
- Цена строго > 0
- Пассажир с указанным ID существует

Для окна добавлен метод `prepareTable`: он читает все бронирования и оставляет только те, что подходят под поиск, статус и город, затем сортирует по дате или цене.

Сортировка через Stream API:
```java
bookings.stream()
    .sorted(Comparator.comparing(Booking::getPrice))
    .collect(Collectors.toList());
```

## 8. Слой пользовательского интерфейса

### ConsoleMenu.java

Это интерфейс КР №1. Окно КР №2 описано в разделе 17. При старте консоли пользователь выбирает роль (1-Администратор, 2-Менеджер, 3-Клиент).
Для клиента дополнительно нужно указать ID пассажира.

Главный цикл:
```java
while (running) {
    switch (currentRole) {
        case ADMIN -> printAdminMenu();
        case MANAGER -> printManagerMenu();
        case CLIENT -> printClientMenu();
    }
    int choice = readInt("Ваш выбор: ");
    switch (currentRole) {
        case ADMIN -> running = handleAdmin(choice);
        ...
    }
}
```

Каждое поле валидируется сразу при вводе. Если ввод некорректен -- система просит повторить, не переходя к следующему полю.

Методы ввода с валидацией:
- readFlightNumber() -- проверяет regex формата рейса
- readCityName() -- проверяет что только буквы/пробелы/дефисы
- readArrivalCity() -- проверяет формат + не совпадает с городом вылета
- readFutureDateTime() -- проверяет формат + не в прошлом + не далее 6 месяцев
- readPositiveDecimal() -- проверяет формат + > 0
- readName() -- только буквы и дефис
- readEmail() -- формат xxx@xxx.xx
- readPhone() -- формат +7-XXX-XXX-XXXX
- readPassport() -- формат XXXX XXXXXX
- readValidatedPassengerId() -- число + существование в БД
- readStatus() -- корректный статус из enum

## 9. Утилитные классы

### DatabaseManager

Одно соединение на все время работы. Приватный конструктор запрещает создание экземпляров.
Метод getConnection() создает соединение при первом вызове или если предыдущее закрыто.
Адрес, пользователь и пароль читаются из `src/main/resources/database.properties`, а не записаны в классе.
Пул соединений не нужен: окно работает в одном потоке, запросы короткие.

### ExcelExporter

Два статических метода: exportToExcel (xlsx с стилями) и exportToCsv (текстовый файл с разделителем ;).
Приватный конструктор -- утилитный класс.

## 10. Собственные исключения

3 исключения, все наследуют RuntimeException:

| Исключение | Когда |
|---|---|
| BusinessRuleException | Нарушение бизнес-правила (цена <= 0, дата в прошлом и т.д.) |
| EntityNotFoundException | Запись не найдена по ID |
| DatabaseException | Ошибка подключения или SQL-запроса |

RuntimeException выбран чтобы не загромождать сигнатуры throws по всей цепочке. Все исключения перехватываются в главном цикле ConsoleMenu.run().

## 11. База данных PostgreSQL

### Таблица passengers

```sql
CREATE TABLE passengers (
    id              BIGSERIAL       PRIMARY KEY,
    first_name      VARCHAR(100)    NOT NULL,
    last_name       VARCHAR(100)    NOT NULL,
    email           VARCHAR(150)    NOT NULL UNIQUE,
    phone           VARCHAR(20)     NOT NULL,
    passport_number VARCHAR(20)     NOT NULL UNIQUE
);
```

BIGSERIAL -- автоинкремент. UNIQUE на email и passport_number.

### Таблица bookings

```sql
CREATE TABLE bookings (
    id              BIGSERIAL       PRIMARY KEY,
    passenger_id    BIGINT          NOT NULL,
    flight_number   VARCHAR(10)     NOT NULL,
    departure_city  VARCHAR(100)    NOT NULL,
    arrival_city    VARCHAR(100)    NOT NULL,
    departure_date  TIMESTAMP       NOT NULL,
    price           DECIMAL(10, 2)  NOT NULL CHECK (price > 0),
    status          VARCHAR(20)     NOT NULL CHECK (status IN ('CREATED','CONFIRMED','COMPLETED','CANCELLED')),
    created_at      TIMESTAMP       NOT NULL DEFAULT NOW(),
    CONSTRAINT fk_booking_passenger
        FOREIGN KEY (passenger_id) REFERENCES passengers (id) ON DELETE CASCADE
);
```

FOREIGN KEY -- связь с passengers. ON DELETE CASCADE -- при удалении пассажира удаляются его бронирования.
CHECK (price > 0) -- защита на уровне БД. DECIMAL(10,2) -- точные десятичные числа для денег.

### Индексы

```sql
CREATE INDEX idx_bookings_passenger_id   ON bookings (passenger_id);
CREATE INDEX idx_bookings_status         ON bookings (status);
CREATE INDEX idx_bookings_flight_number  ON bookings (flight_number);
CREATE INDEX idx_bookings_departure_date ON bookings (departure_date);
```

Ускоряют JOIN, фильтрацию и поиск.

### Связь таблиц

passengers (1) ---- (N) bookings

Один пассажир может иметь много бронирований, каждое бронирование принадлежит одному пассажиру.

## 12. Система ролей

В системе 3 роли (enum UserRole):

### ADMIN (Администратор)
Полный доступ: CRUD пассажиров, CRUD бронирований, поиск, фильтрация, сортировка, статистика, экспорт.

### MANAGER (Менеджер)
CRUD бронирований (любых), просмотр пассажиров (без редактирования), поиск, фильтрация, сортировка, статистика, экспорт.

### CLIENT (Клиент)
Просмотр только своих бронирований, создание бронирования на себя, просмотр своего профиля.

При входе как клиент -- выбирается ID пассажира из списка. Все операции ограничены этим пассажиром.

Роли реализованы через switch в ConsoleMenu: разные меню и обработчики для каждой роли.

## 13. Валидация ввода

Все поля проверяются при вводе через регулярные выражения:

| Поле | Regex | Пример |
|---|---|---|

Дополнительные проверки:
- Город прилета не совпадает с городом вылета
- Дата вылета не в прошлом и не далее 6 месяцев
- Цена строго больше 0
- Пассажир с указанным ID существует в БД

## 15. Принципы ООП

### Инкапсуляция
Все поля моделей private, доступ через геттеры/сеттеры. DatabaseManager -- приватный конструктор и статическое поле.

### Полиморфизм
Интерфейс CrudRepository<T> реализуется PassengerRepository и BookingRepository. Один контракт -- разные реализации.

### Наследование
3 собственных исключения наследуют RuntimeException.

### Абстракция
Интерфейс CrudRepository скрывает детали хранения. Сервис работает с абстракцией.

### Коллекции
List<Booking>, List<Passenger> -- результаты запросов. Map<BookingStatus, Set<BookingStatus>> -- карта переходов. Optional<T> -- результат findById.

### Stream API
Сортировка через stream().sorted(comparator).collect(). Comparator.comparing() с method reference.

## 17. КР №2: настольное JavaFX-приложение

Этот раздел объясняет, как устроено окно и почему выбрано именно так. Его достаточно, чтобы рассказать проект на защите.

### Что изменилось, а что нет

Предметная область та же: пассажир и его бронирования. Таблицы, ограничения, тестовые данные и бизнес-правила КР №1 сохранены. Консольное меню тоже осталось, его запускает `com.airline.Main`.

Новый основной интерфейс — окно. Его запускает `com.airline.fx.AirlineFxApp`. Окно не содержит своих SQL-запросов. Оно вызывает уже готовые `BookingService` и `PassengerService`.

Поэтому правка правила в сервисе сразу действует и в консоли, и в окне. Дублировать проверки в кнопке не нужно.

### Почему не REST и не пример из архива

В методичке есть чужой архив: веб-система, Android и JavaFX-клиент про студентов. Тот JavaFX-клиент ходит на сервер по адресу `http://localhost:8080/api`. Сервер на Spring уже потом пишет в PostgreSQL.

Для своей КР №2 методичка прямо говорит другое: окно подключается через JDBC к базе, сделанной в КР №1. Spring и REST — это следующая контрольная. Если сейчас спрятать базу за сервером, КР №2 будет не про JDBC, а про тему КР №3.

Docker из методички нужен, чтобы один раз поднять и посмотреть тот чужой пример. Наше окно Docker не требует. Ему нужен обычный PostgreSQL с базой `airline_booking` на порту `5432`.

Библиотеки Jackson и SLF4J из готового `pom.xml` методички тоже не добавлены. Jackson превращает JSON ответов сервера в объекты. У нас нет JSON-сервера. Ошибки показываются текстом в диалоге, а не журналом в консоли.

### Почему пароль лежит в properties

В КР №1 адрес базы и пароль были константами в `DatabaseManager`. Для КР №2 так нельзя: пароль не должен быть в исходном коде Java.

`DatabaseManager` при первом подключении читает файл `src/main/resources/database.properties`:

```properties
db.url=jdbc:postgresql://localhost:5432/airline_booking
db.user=postgres
db.password=postgres
```

Maven копирует этот файл в сборку. Класс берет его из classpath, поэтому в программе нет пути вида `C:\Users\...`. Если файла нет или поле пустое, пользователь видит текст, какое именно поле не заполнено.

Файл с паролем все равно лежит в проекте. Для учебной базы `postgres/postgres` это нормально. В настоящей системе пароль был бы в переменной окружения и не попадал бы в Git. Для КР №2 методичка просит именно `database.properties`.

### Слои и путь одного нажатия

Пример: пользователь нажимает «Удалить».

1. В `main-view.fxml` у кнопки написано `onAction="#onDeleteBooking"`.
2. `MainController.onDeleteBooking` проверяет, что строка выбрана, и показывает диалог подтверждения.
3. Если пользователь согласился, контроллер вызывает `bookingService.deleteBooking(id)`.
4. Сервис проверяет, что бронирование существует.
5. `BookingRepository.deleteById` выполняет `DELETE FROM bookings WHERE id = ?` через `PreparedStatement`.
6. Контроллер заново читает список и кладет его в таблицу.

SQL остается в репозитории. Правило «нельзя удалить то, чего нет» остается в сервисе. Контроллер только связывает экран и сервис.

Так же устроены добавление и правка. Форма собирает объект `Booking` и вызывает `createBooking` или `updateBooking`. Регулярные выражения, длина строк, цена, дата и существование пассажира проверяются в сервисе. Форма дополнительно проверяет то, чего сервис не видит в виде отдельных полей: выбран ли пассажир в списке, похоже ли время на `08:30`, является ли цена числом.

### Stage, Scene, Node

- `Stage` — само окно операционной системы. У главного окна заголовок «Бронирование авиабилетов». Формы открываются отдельным `Stage`.
- `Scene` — содержимое окна. В него кладется корневая панель из FXML.
- `Node` — любой элемент внутри сцены: кнопка, таблица, надпись, поле. Панели `BorderPane`, `VBox`, `HBox` тоже узлы, в них лежат другие узлы.

Главное окно создается в `AirlineFxApp.start`. Формы создаются методами `show` у своих контроллеров и открываются модально: пока форма не закрыта, главное окно не принимает нажатия. Так пользователь не запускает второе редактирование поверх первого.

### Зачем FXML, контроллер и fx:id

FXML — это XML-описание экрана: какие панели, кнопки и столбцы таблицы есть и как они стоят. Экран можно прочитать отдельно от Java.

Контроллер — класс, который реагирует на действия. Связь задается в корне FXML:

```xml
fx:controller="com.airline.fx.controller.MainController"
```

`fx:id="bookingTable"` означает: после загрузки FXML положи этот элемент в поле контроллера с тем же именем. Поэтому в `MainController` есть `@FXML private TableView<Booking> bookingTable`.

`onAction="#onSearch"` означает: при нажатии кнопки или Enter в поле поиска вызови метод `onSearch`.

Весь интерфейс не собран в одном классе. Четыре экрана — четыре FXML и четыре контроллера:

| Файл | Класс | Задача |
|---|---|---|
| `main-view.fxml` | `MainController` | таблицы, поиск, фильтры, кнопки |
| `booking-form.fxml` | `BookingFormController` | форма бронирования |
| `passenger-form.fxml` | `PassengerFormController` | форма пассажира |
| `statistics-view.fxml` | `StatisticsController` | шесть показателей |

Общие диалоги ошибки, сообщения и подтверждения удаления вынесены в `FxDialogs`, чтобы один и тот же `Alert` не копировать в каждый контроллер.

### Таблица и ObservableList

`ObservableList` — список, за которым наблюдает JavaFX. Таблица не хранит свои копии строк. В `initialize` ей передают один список:

```java
private final ObservableList<Booking> bookings = FXCollections.observableArrayList();
bookingTable.setItems(bookings);
```

После поиска или сохранения контроллер делает `bookings.setAll(новыйСписок)`. Таблица сама перерисовывается, потому что список наблюдаемый. Отдельный цикл «очисти таблицу и добавь строки по одной» не нужен.

Столбцы описаны в FXML с русскими заголовками. Какой геттер показывать, задается в контроллере. Например, столбец «Рейс» читает `getFlightNumber()`. Цена и дата в списке остаются числом и `LocalDateTime`, а на экране форматируются как `5500.00 руб.` и `15.10.2026 08:30`. Поэтому сортировка по заголовку столбца сравнивает настоящие числа и даты, а не текст.

В таблице нет `passenger_id` и `created_at`. Номер бронирования оставлен: по нему понятно, какую строку обсуждают. Имя пассажира уже приходит из `JOIN` в `BookingRepository`.

Выбор строки слушает `selectedItemProperty`. Когда выбор меняется, нижняя панель заново читает пассажира через `passengerService.getPassengerById` и показывает email, телефон и паспорт. Это просмотр связанной сущности, а не просто фамилия из строки бронирования.

Кнопки «Изменить» и «Удалить» привязаны к выбору: пока строка не выбрана, они неактивны.

### Почему пассажир выбирается из ComboBox

У бронирования есть внешний ключ `passenger_id`. Просить ввести число опасно: легко указать несуществующий id, и пользователю это число ничего не говорит.

`ComboBox<Passenger>` заполняется результатом `passengerService.getAllPassengers()`. На экране строка вида «Иван Петров (4510 123456)». В объект уходит выбранный `Passenger`, а в базу — его `getId()`.

Кнопка «Новый» на форме открывает форму пассажира. После сохранения список обновляется и новый человек уже выбран. Вкладка «Пассажиры» нужна для того же списка и для обратной связи: внизу написано, какие рейсы есть у выбранного человека.

У пассажира и бронирования внешний ключ с `ON DELETE CASCADE`. Удаление пассажира в базе само удаляет его бронирования. Перед этим окно предупреждает, сколько билетов исчезнет вместе с ним.

### Поиск, два фильтра и сортировка

Все четыре действия делает один метод сервиса: `BookingService.prepareTable`.

Поиск — одна строка. Она сравнивается без учета регистра с номером рейса, именем пассажира, городом вылета и городом прилета. Поэтому запрос `петров` и запрос `SU` работают в одном поле.

Фильтры:

- статус: «Все статусы» или одно из четырех русских названий. В сервис уходит `BookingStatus` или `null`;
- город: «Все города» или конкретный город из уже существующих рейсов. Город подходит, если он стоит в вылете или в прилете.

Сортировка в списке — два параметра: дата вылета и цена, каждый по возрастанию и по убыванию. Это обычный `Comparator` и `List.sort`. Цикл с `if` выбран вместо длинной цепочки Stream, чтобы на защите было видно каждое условие отдельно. Старые методы `sortByDepartureDate` и `sortByPrice` из КР №1 остались.

Заголовок столбца сортирует отдельно. Это встроенная сортировка `TableView`: у столбца есть значение, JavaFX сравнивает эти значения и переставляет тот же `ObservableList`. Комбобокс «Сортировка» нужен, чтобы правило сортировки было явным и находилось в сервисе, а не только внутри библиотеки.

Кнопка «Обновить» заново читает базу и применяет текущие поиск и фильтры. После добавления, правки и удаления список тоже перечитывается, выбранная строка по возможности восстанавливается.

### Проверки

Пустые поля, формат, длина, уникальность email и паспорта, положительная цена, разные города, дата не дальше шести месяцев и существование пассажира проверяет сервис. Сообщение — это текст `BusinessRuleException`. Оно попадает в диалог и в красную надпись на форме. Красный стиль — класс `error-text` в CSS.

Новое бронирование всегда получает статус «Создано». Сервис сам ставит его в `createBooking`, даже если форма попробует передать другой.

При редактировании статус меняется отдельно, методом `changeStatus`. В списке только текущий статус и те, в которые из него можно перейти:

- Создано → Подтверждено или Отменено;
- Подтверждено → Завершено или Отменено;
- Завершено и Отменено дальше не меняются.

Сначала сохраняются поля. Потом, если статус другой, вызывается `changeStatus`. Нельзя из формы перескочить через запрещенный переход.

Если дату при редактировании не трогали, проверка «дата не в прошлом» пропускается. Иначе рейсы из тестовых данных, которые уже вылетели, нельзя было бы открыть и сохранить. Новая дата по-прежнему не может быть в прошлом и не может быть дальше шести месяцев.

### Статистика

Окно статистики не считает числа само. Оно вызывает методы сервиса, а те — методы репозитория. SQL остается в `BookingRepository`.

1. Всего бронирований — `COUNT(*)`.
2. Количество по каждому статусу — `GROUP BY status`. Если какого-то статуса нет, на экране показывается 0.
3. Средняя цена — `AVG(price)` по всем бронированиям.
4. Самый частый маршрут — группировка по паре городов, сортировка по количеству, `LIMIT 1`.
5. Пассажир с наибольшим числом бронирований — `JOIN` с пассажирами и такая же сортировка.
6. Выручка — сумма цен только у статусов «Подтверждено» и «Завершено». Созданные и отмененные в выручку не входят.

Показатели считаются по всей базе, а не по отфильтрованной таблице. Это написано в окне статистики, чтобы не путать их с поиском.

### Экспорт

Кнопка выгружает не всю базу, а текущие строки таблицы: то, что осталось после поиска и фильтров.

Путь не записан в коде. `FileChooser` открывает системный диалог, начальная папка — домашняя папка пользователя. Если человек отменил диалог, файл не создается. Если в имени нет `.csv`, расширение добавляется.

Кнопка «Экспорт Excel» вызывает `ExcelExporter.exportToExcel`: файл `.xlsx` через Apache POI, с заголовком и рамками. Кнопка «Экспорт CSV» вызывает `exportToCsv`. Разделитель в CSV — точка с запятой: у русской Excel запятая занята дробной частью. В начало CSV пишется метка UTF-8, иначе кириллица открывается кракозябрами.

### Оформление

`app.css` задает шрифт, фон, заголовок, кнопки основных действий, опасную кнопку удаления, таблицу с синей шапкой, белые формы и красное состояние ошибки. Окно можно сжать до 960 на 640: таблица растягивается вместе с ним, потому что стоит в центре и имеет рост по вертикали.

### Ошибки

Исключения не глотаются пустым `catch`.

- `BusinessRuleException` — неправильный ввод или запрещенный переход статуса;
- `EntityNotFoundException` — запись уже удалили;
- `DatabaseException` — нет связи с базой или сбой SQL.

`ExceptionMessages` достает из цепочки причин код PostgreSQL, если он есть, и заменяет его понятной фразой. В остальных случаях показывается сообщение исключения. Stack trace на экран не выводится.

Если база недоступна уже при старте, окно с таблицей не показывается. Появляется диалог с текстом проверить PostgreSQL и `database.properties`.

### Что сознательно не делалось

- Нет сервера Spring и нет запросов на `localhost:8080`. Это тема КР №3.
- Нет входа по ролям в окне. Роли остались в консоли КР №1. Методичка КР №2 просит CRUD, поиск, фильтры, статистику и экспорт, а не повтор ролевой модели.
- Нет отдельного потока для SQL. Строк мало, запрос мгновенный. Поток `Task` усложнил бы объяснение, не изменив результат.
- Отдельный новый формат экспорта не придумывался: окно вызывает те же `exportToExcel` и `exportToCsv`, что и консоль.
- В один класс не сложены и экран, и SQL, и правила.

## 18. КР №3: сервер Spring Boot

Сервер лежит в каталоге `backend` и не входит в сборку JavaFX. Предметная область та же: пассажир и бронирование. База КР №1 на порту 5432 не используется этим сервером. Docker поднимает отдельный PostgreSQL на `127.0.0.1:56080`.

Схема КР №1 перенесена миграцией Flyway `V1` без `DROP`. Пользователи, архив, теги, заметки и аудит добавляет `V2`. Hibernate схему сам не меняет: `ddl-auto: validate`.

Как объяснять слои, JWT, роли и сценарий защиты: [BACKEND_GUIDE.md](BACKEND_GUIDE.md).
